# 内容审核与举报处理：本地准备稿

这套实现尚未部署或运行。迁移文件为 `supabase/migrations/20261109064127_liya_moderation_queue.sql`。以下操作仅供获授权的 Liya 数据库运营人员在完成独立环境验证和部署后使用；不要把数据库管理员凭据或待审内容放入客户端、聊天或公开文档。

## 行为与边界

- 新的社区帖子及其附件、社区帖子评论、精选图片/视频评论，写入后先进入待审核状态；作者仍可读取自己的内容，其他登录用户不能通过对应表读取，帖子附件的现有 Storage 读取策略也依赖可见的帖子。帖子内容或附件发生修改时重新排队，审核版本加一。
- 社区公开资料的名称、简介和共享头像作为私有待审版本保存；更新期间保留之前通过的公开资料，新用户先显示中性资料。审核通过后才替换公开版本；用户取消头像共享时立即移除公开头像引用，不等待审核。普通账号资料仍为本人私有。审核员也可隐藏或恢复违规的公开资料，关系和原始资料不删除；隐藏期间其他用户可能无法打开资料或发起新聊天。
- 现有内容不自动批量隐藏；必要时审核员可单独隐藏，原始内容不删除。精选图片/视频的隐藏保留目录和排序，仅限制重新获取文件，避免点赞和评论错位；预设评论需要单独隐藏，素材元数据仍可见。已签发的 Storage 临时链接在到期前可能仍可用，客户端当前签发时长为一小时，已下载或缓存的内容也无法由此收回。帖子评论通知改为审核通过后发送；通知、缓存和旧客户端行为仍需在实际服务中验证。
- 默认采用人工审核，不含自动识别；审核员必须检查文字、标签、公开资料、头像及每个图片、视频附件。既有精选素材不自动进入先审队列，需要另行处理。新提交的公开内容在有人审核前不会对其他用户公开，因此上线前必须有真实值守和处理时限。
- 现有举报和新举报汇入私有队列；社区评论新增单独举报，图片评论的举报策略扩展到图片。私聊不会自动进入审核；接收者主动举报后，仅该条消息的文本及附件引用交给审核员，界面需在提交前说明。提交举报只创建待处理记录，不会因为单个用户的举报自动下架。
- App 显示作者自己的待审核或未通过状态，也在“Privacy → Submitted reports”中显示本人举报的处理状态；取不到状态时明确显示不可用。记录被审核不代表已经通过邮箱回复举报人，邮箱及运营回复流程仍需实际落实。你已确认本人负责审核，但实际值守和处理尚未验证。
- 处理函数限定数据库可信操作员调用，并带版本校验及操作记录。操作员名称是由管理人员输入的标识，不是经过独立认证的实名身份。直接使用数据库管理员权限修改表可绕过这些函数，必须按组织权限制度管理。

## 处理队列

在 Liya 项目的 Supabase SQL Editor 以获授权的管理角色执行下列只读查询。以下数据可能包含用户内容，仅在受控环境查看。

```sql
-- 待审内容；图片和视频的路径仅供授权审核员在 Storage 中查看。
select m.kind, m.content_id, m.revision, m.submitted_at,
       pr.display_name as proposed_name, pr.signature as proposed_signature, pr.avatar_path as proposed_avatar,
       p.body as post_body, p.tags, p.media_paths, p.media_kinds,
       c.body as post_comment, v.body as media_comment, v.media_id
from liya_social_private.moderation_content m
left join liya_social_private.moderation_profiles pr on m.kind = 'profile' and pr.owner_id = m.content_id
left join public.liya_posts p on m.kind = 'post' and p.id = m.content_id
left join public.liya_post_comments c on m.kind = 'post_comment' and c.id = m.content_id
left join public.liya_video_comments v on m.kind = 'media_comment' and v.id = m.content_id
where m.status = 'pending'
order by m.submitted_at, m.kind, m.content_id;
```

检查完整内容与附件，按社区标准决定。复制查到的 `kind`、`content_id`、`revision`，将下面的占位值替换为本次实际值。不要更改决定函数内部逻辑：

```sql
-- 通过填 approved；不通过填 rejected。返回 false 表示内容已变化、已处理或不存在，应重新读取。
select liya_social_private.review_content('post', '<content UUID>'::uuid, 1, 'approved', '<审核员标识>');
```

被隐藏或拒绝的内容可在重新检查后以其当前 revision 和 `approved` 恢复。帖子修改会递增 revision 并重新排队；评论不能编辑，作者可删除后重新提交。

资料待审项的 `kind` 是 `profile`；审核时查看名称、简介和头像，使用相同的 `review_content` 函数与当前 revision。资料修改会递增 revision；旧版本 App 在新迁移部署后可能不能正确识别待审回读，必须先核验版本兼容和发布顺序。

```sql
-- 举报复核后，必要时隐藏已有或已通过的帖子/评论；kind 使用 post、post_comment 或 media_comment。
select liya_social_private.hide_content('post', '<content UUID>'::uuid, '<审核员标识>');
```

```sql
-- 隐藏违规公开资料；确认可恢复后用 false 恢复。操作不会删除资料或关系。
select liya_social_private.set_profile_hidden('<user UUID>'::uuid, true, '<审核员标识>');
```

```sql
-- 使用举报里的 curated_media_id；true 限制新文件访问，false 恢复。返回 false 表示素材不存在。
select liya_social_private.set_curated_hidden('<media ID>', true, '<审核员标识>');

-- 查询当前受限素材和最近的操作记录。
select h.media_id, m.kind, h.hidden_at
from liya_social_private.hidden_curated_media h
join public.liya_example_media m on m.id = h.media_id
order by h.hidden_at;
select media_id, decision, actor, created_at
from liya_social_private.curated_moderation_events
order by created_at desc;
```

此操作只影响采用普通登录角色重新申请文件的请求；已签发链接、缓存及有管理员权限的访问不受此限制。目录位置仍然保留，界面可能显示不可用的占位，不能当作立即从所有设备清除。请在独立环境验证隐藏、恢复、缓存与旧版本行为。

```sql
-- 视频预设评论的 preset_key 形如 <media ID>:starter:0 或 :starter:1。
-- 填入举报中的视频 media ID 和末尾的数字；false 可恢复。
select liya_social_private.set_curated_starter_hidden('<media ID>', 0, true, '<审核员标识>');
select media_id, position, hidden_at from liya_social_private.hidden_curated_starters order by hidden_at;
select media_id, position, decision, actor, created_at from liya_social_private.curated_starter_events order by created_at desc;
```

新版 App 读取处置状态后才显示预设评论，查询失败时不展示预设评论；需要部署迁移并发布新版后才可生效。预设文字已经打包在旧版 App 内，旧版不会遵循这个开关，仍需通过版本升级或停止展示相应功能处置。该机制不能从已安装的旧版 App 中抹除文字。

## 查看举报

```sql
select q.kind, q.report_id, q.created_at,
       s.target_user, s.post_id, s.reason as social_reason,
       e.media_id as curated_media_id, e.target_type, e.reason as curated_reason,
       v.media_id as comment_media_id, v.comment_id as media_comment_id, v.preset_key, v.body_snapshot as media_comment_body, v.reason as media_comment_reason,
       c.comment_id as post_comment_id, c.post_id as comment_post_id, c.target_user as comment_author, c.body_snapshot as post_comment_body, c.reason as post_comment_reason,
       dm.message_id, dm.target_user as message_sender, dm.body_snapshot as reported_message,
       dm.media_paths as message_attachments, dm.media_kinds as message_attachment_kinds, dm.reason as message_reason
from liya_social_private.moderation_reports q
left join public.liya_social_reports s on q.kind = 'social' and s.id = q.report_id
left join public.liya_content_reports e on q.kind = 'curated' and e.id = q.report_id
left join public.liya_video_comment_reports v on q.kind = 'media_comment' and v.id = q.report_id
left join public.liya_post_comment_reports c on q.kind = 'post_comment' and c.id = q.report_id
left join public.liya_message_reports dm on q.kind = 'message' and dm.id = q.report_id
where q.status = 'pending'
order by q.created_at, q.kind, q.report_id;
```

社区用户举报可能没有 `post_id`；带帖子的举报在提交时要求帖子可见且属于被举报人，可先调查再按需隐藏资料或帖子。私聊举报仅含接收者主动选中的单条消息及附件引用，附件可能因发送者删号而不可用；不能借此浏览其他私聊。精选素材可用上面的函数限制新文件访问；预设评论的举报文字快照由客户端提交，审核时应对照 App 内原文，不能直接视为可信证据。举报原始记录因账号删除而被级联清理时，相应队列和处理记录也会清理；不要将队列当作永久留存工具。

```sql
-- 在调查并执行必要处置后标记 resolved；不成立的举报可标记 dismissed。
select liya_social_private.review_report('social', '<report UUID>'::uuid, 'resolved', '<审核员标识>');
```

`moderation_events` 保存由上述函数产生的操作时间、输入的审核员标识和决定；对应源内容或举报被删除时记录一并清理。它不替代账号级管理员访问日志、告警或运营交接。当前没有自动邮件通知、面向审核员的独立控制台或逐项处理说明；举报人可在 App 内查看状态。

## 上线前验收

1. 比对线上实际结构与本地所有前置迁移，备份并在独立非生产环境验证迁移、RLS、Storage 与 Realtime；确认旧版本客户端行为和异常重试。不得直接把未经验证的策略应用到生产。
2. 使用两个测试账号及获授权的审核员，覆盖资料新建与重复 upsert、头像修改、旧公开资料保留、审核通过/拒绝及资料隐藏/恢复；覆盖新帖、帖子修改、图片/视频附件、社区评论、图片/视频评论、私聊单条举报、拉黑、并发修改和旧内容隐藏/恢复。确认待审内容不会被其他账号读取，拒绝后作者有明确提示，附件和计数不泄露；未举报私聊不得进入队列。
3. 检查账号删除、内容删除、报告删除、审核记录清理、精选素材和预设评论隐藏与恢复、签名 URL 过期、同步刷新与运营通知。确认隐藏素材不能获得新的签名链接、其他素材和其他 bucket 不受影响；新版预设评论查询失败时不展示，旧版行为单独确认。确认旧链接及缓存的实际行为符合预期；确认报告无法伪造其他用户或引用无权查看的真实用户评论。
4. 指定实际值守人、支持邮箱、审核标准、响应时限和恢复流程，验证邮箱收发。审核团队真正到位之后，再更新 App 内当前“审核未配置”的提示并重新生成、发布协议 PDF。

### 发布顺序和回退注意事项

- 先在隔离环境核验迁移和新旧客户端，再安排协调发布。新版客户端的资料编辑依赖 `liya_my_profile_submission`，不能先于该迁移投入使用；迁移先上线也可能让旧版客户端把已排队的资料修改误判为失败，必须先确认旧版本兼容性和可接受的过渡方式。当前方案没有版本开关，也不能保证零停机升级。
- 正式变更前核对项目、迁移历史、数据库备份及恢复方式，并确保审核员能处理积压。任何线上执行应使用正规迁移流程，不能把本文占位命令原样复制到生产。
- 如上线后出现问题，先暂停新增发布并保全待审核资料、举报和操作记录，再按事先验证的恢复方案处理；不要直接删除队列表、关闭 RLS 或回退到可能公开待审内容的状态。此前签发的链接和客户端缓存也须单独评估。
